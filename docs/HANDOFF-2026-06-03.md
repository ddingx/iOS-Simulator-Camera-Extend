## 0.1 最终修复（2026-06-03 20:58，已由用户复测确认）

QuickTime 里的"扫描线"不是视频噪声，而是 `SimCamCMIOStreamSource.tickDemo()` 自带的 fallback/demo 帧。它能出现，说明 **source stream 已经被 QuickTime 成功启动**；真正没通的是 host app → CMIO sink stream → sysext `consumeSampleBuffer` 这条回灌链路。

最终根因：host 端 `CMIOSinkClient.findSinkStream()` 只按 `kCMIOStreamPropertyDirection == 1` 猜 sink stream。实测这个判断不可靠，会选到错误的 stream/queue；随后第一帧开始 `CMSimpleQueueEnqueue` 就返回 `-12773`，也就是 `kCMSimpleQueueError_QueueIsFull`。队列从第一帧就是满的，同时 sysext 端没有 `SimCam sink startStream entered` / `consumeSampleBuffer`，证明 host 实际没启动真正的 `SimCam.Sink`。

有效修复在 [Sources/SimCamCore/CMIOSinkClient.swift](file:///Users/guoshuyu/workspace/swmansion-copy/Sources/SimCamCore/CMIOSinkClient.swift)：

- `findSinkStream(deviceID:)` 枚举 device streams 时打印每个 candidate 的 `index / id / name / direction`
- 优先按 stream name 选择包含 `sink` 的 stream，也就是 sysext 端发布的 `SimCam.Sink`
- 如果没有 name 命中，再按 `addStream(source)` → `addStream(sink)` 的顺序选择第二条 stream
- `direction == 1` 只保留为最后 fallback，不能再作为主判断
- `push(_:)` 在 enqueue 前检查 `CMSimpleQueueGetCount` / `CMSimpleQueueGetCapacity`
- 遇到队列已满或 `kCMSimpleQueueError_QueueIsFull` 立即 `resetSinkConnection(...)` + rediscover，不能继续向错误 queue 狂塞帧

复测通过后的关键日志形态：

```text

stream candidate index=... id=... name=SimCam.Sink direction=...
selected sink stream by name: ...

cmio sink push #1
cmio sink alteredProc ack
SimCam stream: switched from demo to host frames (sink)
```

这次用户确认 QuickTime 画面已经从扫描线切到真实 camera。后续不要再把"扫描线"当成 source stream 没发布，也不要再回到 IOSurface / framesock / entitlement 猜测；先看 `selected sink stream by name` 和 `SimCam sink startStream entered` 是否存在。

## 1. 项目目标

- macOS host app `SimCamApp` + 一个 CMIO Camera Extension `dev.simcam.app.extension`，对外发布一个 **SimCam Virtual Camera**
- 路线（Apple 官方）：host → CMIO **sink stream**（CMSimpleQueue + `CMIODeviceStartStream` + `CMIOStreamCopyBufferQueue`） → sysext 内 `consumeSampleBuffer` → 同 sysext 的 source stream 出帧 → 任意 AVFoundation 客户端（QuickTime / FaceTime / iOS Simulator）看到 host 摄像头真画面
- 非目标 / 不要再退回的方案：
  - ❌ IOSurface + Darwin notify 桥（sandbox EPERM `/tmp` + Group Container 跨进程隔离，已证伪）
  - ❌ framesock IPC 替代 CMIO（用户严禁——"我们就是做 CMIO，你放弃 CMIO 那还做什么"）

## 7. 已解释并修复的核心问题

### 7.1 P0 — host 能看到 device，但选错了 stream queue

旧文档一度把问题描述成 "host 进程 enumerate 看不到自家 device"。后续实测里 host 已经能通过 AVFoundation + HAL 反查到 `SimCam Virtual Camera` 和 `CMIODeviceID`；真正坏点发生在下一步：从 device 的 streams 里挑 sink stream。

错误代码路径是只相信 `kCMIOStreamPropertyDirection == 1`。这在当前 CMIO Camera Extension 场景不可靠：它会把 host 带到错误 queue，表现为第一帧 `CMSimpleQueueEnqueue` 就失败：

```text
CMSimpleQueueEnqueue failed status=-12773
```

`-12773` 是 CoreMedia `kCMSimpleQueueError_QueueIsFull`。如果队列从第一帧开始就是满的，同时 sysext 端没有 `SimCam sink startStream entered`，就不要继续查权限、签名、App Group 或 QuickTime；优先检查 host 是否选中了真正的 `SimCam.Sink`。

### 7.2 P1 — sink stream 的 `consumeSampleBuffer` 双握手已经触发

修复后链路是：

```text
SimCamApp CMIOSinkClient
  -> CMIOStreamCopyBufferQueue(real SimCam.Sink)
  -> CMIODeviceStartStream(real SimCam.Sink)
  -> CMSimpleQueueEnqueue
  -> SimCamExtension SimCamCMIOSinkSource.startStream()
  -> consumeSampleBuffer(from:)
  -> SimCamCMIOStreamSource.handleRealSampleBuffer()
  -> source stream.send(...)
  -> QuickTime sees real camera
```

`shouldEnqueue` / `CMIODeviceStreamQueueAlteredProc` 双握手仍然需要保留。它不是这次扫描线的根因，但它是防止 queue 堆满、保证 cmiod 持续消费 host samples 的流控机制。
